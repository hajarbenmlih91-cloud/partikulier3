1. Executive summary

The codebase shows a mature security posture in many areas: nonce-checked AJAX handlers, prepared SQL, an explicit permission_callback on every REST route (enforced by a static contract), a whitelisted and hash-pinned command-execution gateway, careful upload validation, and constant-time secret comparison. No real secret, API key or private key was found in the working tree or in any of the 75 commits of Git history.

However, one high-severity business-logic flaw lets an unauthenticated visitor take over an existing WordPress account, including editor or administrator accounts. When an administrator approves a listing that the attacker submitted with the victim's e-mail address, the site resets the victim's password and sends the new one to the attacker's WhatsApp number. This was reproduced end-to-end on the local stack.

F-01 — Account takeover via anonymous deposit + admin approval HIGH

Files
theme/partikulier/inc/class-form.php L424-437, L782-786 · theme/partikulier/inc/class-listing-approval.php L306-345, L403-446, L482-570
Entry point
POST /wp-admin/admin-ajax.php?action=pk_submit_listing (wp_ajax_nopriv_pk_submit_listing): public, nonce available on the public deposit page
CWE
CWE-640 (Weak Password Recovery Mechanism), CWE-639 (Authorization Bypass Through User-Controlled Key), CWE-284
CVSS 3.1 (est.)
AV:N/AC:H/PR:N/UI:R/S:U/C:H/I:H/A:H ≈ 7.5 (UI:R = an admin must approve the listing or click “New password”)
Status
✅ Reproduced on local Docker stack

Description

The public deposit flow calls ensure_user() with the e-mail typed by the (anonymous) visitor. If a WordPress user already owns that e-mail, that existing account is returned and becomes the author of the pending listing, whatever its role:

// theme/partikulier/inc/class-form.php  L782-786
private static function ensure_user( $email, $name ) {
    $user = get_user_by( 'email', $email );
    if ( $user && false === strpos( $email, '@partikulier.local' ) ) {
        return $user;                          // ← any existing account, no ownership proof
    }
    ...

The attacker also controls the owner phone number (_pk_owner_phone). When an administrator approves the listing (approve()) or clicks New password (handle_resend()), prepare_credentials() resets the author's password without any role or provenance check. It then sends login and password to n8n, which delivers them over WhatsApp to the phone number supplied by the attacker:

// theme/partikulier/inc/class-listing-approval.php  L403-446
public static function prepare_credentials( $post_id, $force = false ) {
    $user = get_user_by( 'id', get_post_field( 'post_author', $post_id ) );
    ...
    $already = get_user_meta( $user->ID, '_pk_credentials_sent', true );
    if ( $already && ! $force ) { ... return without password ... }
    $password = self::readable_password();
    wp_set_password( $password, $user->ID );   // ← no role / origin check (editor, admin…)
    ...
    return array( 'login' => $user->user_login, 'phone' => $resolved_phone, 'password' => $password, ... );

Accounts that never received deposit credentials (all staff accounts, every normal WordPress user) have no _pk_credentials_sent meta, so the first approval always resets them. The New password button ($force = true) resets even accounts that already have the meta.

Attack scenario

  1. Attacker learns a staff e-mail (contact page, WHOIS, author meta in feeds, social engineering, or guessing contact@/admin@).
  2. Attacker submits an attractive listing on /deposer/ with email = victim@domain and phone = attacker's WhatsApp.
  3. The listing appears in Partikulier → Valider les annonces like any other deposit; the admin approves it.
  4. The victim's password is replaced and sent to the attacker. The victim is locked out, and the attacker logs in with the victim's role. For an administrator this means full site compromise (plugin upload leads to remote code execution).

Evidence (local PoC output)

1. anonymous deposit attributed to user #4 roles=editor (victim #4)
2. prepare_credentials: login=victim_editor phone=212600000000 password_len=10
3. old password still valid? NO
4. new password (sent to attacker phone) valid? YES

Secondary impacts

  • Content impersonation: listings (and their public owner page, stats, e-mails) can be attributed to any registered person without consent.
  • Denial of access: even without receiving the password, the victim is locked out after approval.
  • Plaintext credentials at rest in third-party systems: the password persists in n8n execution logs and WhatsApp history (see F-02).

Recommended fix (defense in depth: apply all three)

1 — Never attach an anonymous deposit to an existing account. Require the owner of that e-mail to be logged in, and tag accounts created by the deposit flow:

// theme/partikulier/inc/class-form.php
private static function ensure_user( $email, $name ) {
    $user = get_user_by( 'email', $email );
    if ( $user && false === strpos( $email, '@partikulier.local' ) ) {
-       return $user;
+       if ( is_user_logged_in() && get_current_user_id() === (int) $user->ID ) {
+           return $user;
+       }
+       return new WP_Error(
+           'pk_email_in_use',
+           __( 'Cette adresse e-mail est déjà associée à un compte. Connectez-vous pour déposer une annonce.', 'partikulier' )
+       );
    }
    $login    = sanitize_user( strtok( $email, '@' ) . wp_rand( 1000, 9999 ) );
    $password = wp_generate_password( 16, true, false );
    $user_id  = wp_create_user( $login, $password, $email );
    if ( is_wp_error( $user_id ) ) {
        return $user_id;
    }
+   update_user_meta( $user_id, '_pk_deposit_account', 1 );
    ...

Returning a generic message avoids turning the form into an e-mail enumeration oracle only if the same message is also used for other failures. Alternatively, accept the deposit but create a new placeholder account and ask the real owner to claim it by e-mail link.

2 — Refuse password resets for anything that is not a deposit-created, low-privilege account:

// theme/partikulier/inc/class-listing-approval.php
+ private static function may_issue_credentials( WP_User $user ) {
+     if ( user_can( $user, 'edit_others_posts' ) || user_can( $user, 'list_users' ) || user_can( $user, 'manage_options' ) ) {
+         return false;                                   // staff accounts: never

+     if ( array_diff( (array) $user->roles, array( 'contributor', 'subscriber' ) ) ) {
+         return false;                                   // unexpected role
+     }
+     return (bool) get_user_meta( $user->ID, '_pk_deposit_account', true );
+ }

  public static function prepare_credentials( $post_id, $force = false ) {
      $user = get_user_by( 'id', get_post_field( 'post_author', $post_id ) );
      ...
+     if ( ! self::may_issue_credentials( $user ) ) {
+         return array(
+             'user_id' => $user->ID, 'login' => $user->user_login, 'email' => $user->user_email,
+             'display_name' => $user->display_name, 'phone' => $resolved_phone,
+             'password' => '', 'reused' => true, 'blocked' => 'not_a_deposit_account',
+             'login_url' => pk_login_page_url(),
+         );
+     }
      $already = get_user_meta( $user->ID, '_pk_credentials_sent', true );
      ...

Migration: existing deposit accounts lack _pk_deposit_account. Backfill once with WP-CLI for contributors that already received credentials or authored a deposit:

wp user list --role=contributor --field=ID | while read id; do
  wp user meta update "$id" _pk_deposit_account 1
done

3 — Stop sending passwords; send a one-time set-password link (also closes most of F-02's credential exposure):

+ $key = get_password_reset_key( $user );              // single-use, expires (default 24 h)
+ if ( is_wp_error( $key ) ) { return ...; }
+ $set_url = network_site_url( 'wp-login.php?action=rp&key=' . rawurlencode( $key ) . '&login=' . rawurlencode( $user->user_login ), 'login' );
- wp_set_password( $password, $user->ID );
  ...
- 'password'  => $password,
+ 'set_password_url' => $set_url,

The admin screen should also show a visible warning whenever the listing author is not a deposit account (role, registration date, number of existing listings).

Verification

  • Re-run the PoC in the Appendix: step 1 must return WP_Error pk_email_in_use. Calling prepare_credentials() on an editor-authored post must return blocked, and the old password must stay valid.
  • Add a contract (e.g. tests/se0xx-credentials-takeover-contract.php) asserting both behaviours and wire it in contrats-recette.yml.

F-02 — Shared automation secret sent on every outbound webhook MEDIUM

Files
plugin/partikulier-core/src/Domain/Automation/AutomationHmacTrait.php L49-73, L84-161 · theme/partikulier/inc/class-listing-approval.php L482-570
CWE
CWE-522 (Insufficiently Protected Credentials), CWE-294 (Authentication Bypass by Capture-replay), CWE-319 adjacent
CVSS 3.1 (est.)
AV:N/AC:H/PR:H/UI:N/S:U/C:H/I:H/A:N (requires access to n8n logs, a proxy, or the webhook receiver)

Description

outgoing_headers() signs the body with HMAC (good), but also sends the raw shared secret in X-Partikulier-Automation. That same secret is what check_automation_secret() accepts on the inbound routes (/automation-event, /contact-authorization, /preferences, /consent, /opt-out, /approved-listings). The HMAC key is derived from that same secret, so anyone who sees one outbound request (n8n execution history, reverse-proxy or WAF logs, a mis-pointed webhook URL) can:

  • call the inbound routes with a valid shared secret, and
  • compute valid HMAC signatures, which defeats hmac_mode=enforce.
// AutomationHmacTrait.php L66-72
return [
    'Content-Type'             => 'application/json',
    'X-Partikulier-Automation' => $secret,           // ← raw secret leaves the site
    'X-Partikulier-Timestamp'  => $timestamp,
    'X-Partikulier-Key-Id'     => $key_id,
    'X-Partikulier-Signature'  => 'sha256=' . hash_hmac('sha256', $canonical, self::hmac_key($secret)),
];

In addition:

  • The listing-approval webhook payload carries the plaintext account password (account.password), which persists in n8n execution data and WhatsApp history. This is documented as a product choice, but combined with F-01 it turns into account takeover. Prefer a single-use set-password link (see F-01 fix #3).
  • The inbound signature check has a 300-second window but no replay cache: a captured signed request can be replayed within 5 minutes (partly mitigated by event-level idempotency on /automation-event, but not on every route).
  • Comparison trims = from both sides (trim(..., '=')), a minor normalisation that slightly widens the accepted token space. Low impact.

Recommended fix

1 — Never transmit the secret; authenticate outbound calls by signature only, ideally with a dedicated outbound key (outbound_signing_secret) distinct from the inbound key:

// AutomationHmacTrait::outgoing_headers()
  return [
      'Content-Type'             => 'application/json',
-     'X-Partikulier-Automation' => $secret,
      'X-Partikulier-Timestamp'  => $timestamp,
      'X-Partikulier-Key-Id'     => $key_id,
      'X-Partikulier-Signature'  => 'sha256=' . hash_hmac('sha256', $canonical, self::hmac_key($secret)),
  ];

Matching n8n Code node (verification on the receiving side):

const crypto = require('crypto');
const h = $input.first().json.headers;
const ts = h['x-partikulier-timestamp'];
if (Math.abs(Date.now() / 1000 - Number(ts)) > 300) throw new Error('stale');
const path = new URL($input.first().json.webhookUrl).pathname;      // must match what WordPress signed
const canonical = `POST\n${path}\n${ts}\n${JSON.stringify($input.first().json.body)}`; // use the RAW body if available
const key = Buffer.from($env.PK_OUTBOUND_SECRET, 'base64');
const expected = 'sha256=' + crypto.createHmac('sha256', key).update(canonical).digest('hex');
if (!crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(h['x-partikulier-signature'] || ''))) throw new Error('bad signature');
return $input.all();

2 — Add a replay cache on inbound signed requests (respecting the double-execution of permission_callback handled by RequestCycle):

// inside check_automation_secret(), after $valid = hash_equals(...) succeeds
+ if ( $valid && RequestCycle::first_run( $request, 'hmac_replay_check' ) ) {
+     $replay_key = 'pk_hmac_seen_' . hash( 'sha256', $key_id . '|' . $signature );
+     if ( false !== get_transient( $replay_key ) ) {
+         $valid = false;                                    // replayed request
+     } else {
+         set_transient( $replay_key, 1, 600 );              // > 2 × timestamp window
+     }
+ }

3 — Operations: rotate the current automation_api_secret after deploying the fix (it has been sent in clear headers to n8n since B4), purge n8n execution data containing account.password, and set a short execution-data retention in n8n.

Verification

  • Capture an outbound request (e.g. with a local HTTPS request bin): no X-Partikulier-Automation header, only timestamp, key-id and signature headers.
  • Send the same signed inbound request twice within 300 s: the second must return 401 and increment pk_n8n_hmac_audit.

F-03 — REST rate-limiter bypass via per-ID buckets MEDIUM

File
plugin/partikulier-core/src/RateLimiter.php L19-25, L64-69
CWE
CWE-770 (Allocation of Resources Without Limits), CWE-799 (Improper Control of Interaction Frequency)
CVSS 3.1 (est.)
AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:L ≈ 5.3
Status
✅ Reproduced

Description

The bucket key includes the concrete route ($request->get_route()), e.g. /partikulier/v1/listings/123. Every distinct ID therefore gets a fresh quota, so the 180 req/min public limit on GET /listings/{id} never triggers for a scraper walking IDs. Each miss also creates a new APCu entry or transient (wp_options rows when APCu is absent), which is a storage-amplification vector.

$route = preg_replace('/[^a-z0-9_-]/i', '_', $request->get_route()) ?: 'route';
$key   = 'pk_rl_' . md5($bucket . '|' . $route . '|' . $identity);   // ← route contains the ID

Evidence (local PoC, limit 180/min)

distinct ids : allowed=400 blocked=0
same id      : allowed=180 blocked=220

Related (DP-4, documented as open): identity is REMOTE_ADDR. Behind the Hostinger CDN every anonymous visitor may share the proxy IP, so one abuser can exhaust the quota for everyone (a denial of service on the /leads 10/min bucket and on the deposit form's 5/h limit in class-security.php:84).

Recommended fix

// RateLimiter::guard()
- $route = preg_replace('/[^a-z0-9_-]/i', '_', $request->get_route()) ?: 'route';
+ $route = (string) $request->get_route();
+ $route = preg_replace('#/\d+(?=/|$)#', '/{id}', $route);          // collapse numeric path params
+ $route = preg_replace('/[^a-z0-9_{}-]/i', '_', $route) ?: 'route';

Optionally add a second, coarser bucket per identity across the whole namespace (e.g. 600 req/min) to cap total load. For DP-4, implement a trusted-proxy resolver that only honours X-Forwarded-For / CF-Connecting-IP-style headers when REMOTE_ADDR is inside a configured CIDR allow-list of the CDN (constant in wp-config.php). Otherwise keep REMOTE_ADDR, as the project's engineering rule already requires.

Verification

Re-run the PoC: “distinct ids” must be blocked after 180. Extend core-contract.php (CORE-RATE-00x) with a varying-ID case.

F-05 — Content-Security-Policy allows inline scripts LOW

File
theme/partikulier/inc/class-security.php L72
CWE
CWE-1021 / defense-in-depth for CWE-79

script-src 'self' 'unsafe-inline' https://static.addtoany.com means any HTML-injection bug (in the theme, Estatik or another plugin) becomes executable script. No XSS was found in the reviewed templates: output is consistently escaped, and the three raw echos (header.php:60,65, card-property.php:149) are built from escaped fragments or core functions. The CSP is therefore the second line of defence, and it is currently ineffective against inline script.

Recommended fix

  1. Move inline JS into enqueued files, or emit it via wp_add_inline_script().
  2. Add a per-response nonce through the wp_inline_script_attributes and wp_script_attributes filters (WP ≥ 5.7), and replace 'unsafe-inline' with 'nonce-…' 'strict-dynamic'.
  3. Because the theme has a full-page cache (a nonce baked into cached HTML is static), either exclude pages with inline scripts from the cache or use 'sha256-…' hashes of the fixed inline blocks.
  4. Roll out as Content-Security-Policy-Report-Only with a report-to endpoint first.

F-06 — Listing view counter trivially inflatable LOW

File
theme/partikulier/inc/class-dashboard.php L69-90 (wp_ajax_nopriv_pk_views_counter)
CWE
CWE-837 (Improper Enforcement of a Single, Unique Action)

Deduplication relies only on a client-side cookie pk_v_{id}. A script that drops cookies can inflate _pk_views without limit, which skews owner statistics (and any premium or ranking logic that uses them). Each hit also does a non-atomic read-modify-write on post meta, so concurrent increments are lost. The nonce comes from public (cached) pages, so it is not a meaningful barrier.

Recommended fix

+ $ip   = isset( $_SERVER['REMOTE_ADDR'] ) ? (string) $_SERVER['REMOTE_ADDR'] : '';
+ $ua   = isset( $_SERVER['HTTP_USER_AGENT'] ) ? substr( (string) $_SERVER['HTTP_USER_AGENT'], 0, 200 ) : '';
+ $seen = 'pk_vw_' . hash_hmac( 'sha256', $post_id . '|' . $ip . '|' . $ua, wp_salt( 'nonce' ) );
+ if ( ! isset( $_COOKIE[ $cookie_key ] ) && false === get_transient( $seen ) ) {
+     set_transient( $seen, 1, DAY_IN_SECONDS );
+     global $wpdb;                                    // atomic increment
+     $wpdb->query( $wpdb->prepare(
+         "UPDATE {$wpdb->postmeta} SET meta_value = meta_value + 1 WHERE post_id = %d AND meta_key = '_pk_views'", $post_id ) );
+     clean_post_cache( $post_id );
+ }

Also ignore known bots (User-Agent heuristics) and apply the same per-IP limiter as the REST layer. Prefer storing the counter in a dedicated table (the plugin already owns pk_property_saves-style tables).

F-07 — Encryption keys derived from WordPress salts; legacy CBC without MAC LOW

Files
theme/partikulier/inc/class-crypto.php L36, L60-84 · theme/partikulier/inc/class-listing-approval.php L363, L386 · plugin/src/Domain/Leads/LeadsPrivacyTrait.php (same scheme)
CWE
CWE-320 (Key Management Errors), CWE-353 (Missing Support for Integrity Check)
  • hash('sha256', wp_salt('secure_auth'), true) ties personal-data encryption to the login-cookie salts. Rotating salts, which is standard incident response after a compromise, permanently destroys every encrypted phone number. Operators may therefore avoid rotating salts when they should.
  • The same salt material is used for session cookies and data encryption, so there is no key separation.
  • The legacy AES-256-CBC fallback has no MAC. Decryption is admin-only, so padding-oracle exploitation is impractical, but unauthenticated ciphertext should be migrated away.
  • Envelope gcm:v1: has no key identifier, which makes rotation impossible.

Recommended fix

// wp-config.php (generated once: php -r 'echo base64_encode(random_bytes(32));')
define( 'PARTIKULIER_DATA_KEYS', array( 'k2' => 'BASE64_32_BYTES…' ) );   // newest first
define( 'PARTIKULIER_DATA_KEY_ACTIVE', 'k2' );

// crypto helper
$ikm = base64_decode( PARTIKULIER_DATA_KEYS[ $kid ], true );
$key = hash_hkdf( 'sha256', $ikm, 32, 'partikulier:phone:v2' );          // key separation per purpose
return 'gcm:v2:' . $kid . ':' . base64_encode( $iv . $tag . $ciphertext );

Keep reading gcm:v1 and CBC through the salt-derived key during a WP-CLI re-encryption migration, then remove the CBC branch.

F-08 — Environment-variable name drift for the n8n secret LOW

Files
plugin/src/Domain/Automation/AutomationPolicyTrait.php L50-56 · theme/inc/class-settings.php L335-338 · docs/INSTALLATION.md (“Configuration sensible”) · theme/inc/class-automation-bridge.php L75
CWE
CWE-1188 (Insecure Default Initialization) / configuration error

The documentation tells operators to inject PARTIKULIER_AUTOMATION_API_SECRET. The theme reads that name, but the plugin, which owns the automation domain since B4, reads PARTIKULIER_N8N_SECRET. An operator following the docs believes the secret comes from the environment, while the plugin actually uses whatever is stored in pk_n8n_settings (plaintext in the database and possibly a stale staging secret). The result is secret reuse across environments and unexpected authentication behaviour.

Recommended fix

public static function env_secret(): string
{
+   foreach ( array( 'PARTIKULIER_N8N_SECRET', 'PARTIKULIER_AUTOMATION_API_SECRET' ) as $name ) {
+       if ( defined( $name ) && constant( $name ) ) { return (string) constant( $name ); }
+       $value = getenv( $name );
+       if ( false !== $value && '' !== $value ) { return (string) $value; }
+   }
+   return '';
}

Document a single canonical name. Show in the admin settings screen whether the secret comes from the environment or the database, and when it was last rotated. Store the option with autoload = no.

6. Controls already done well

  • REST authorisation: every route in partikulier/v1 is declared through RouteRegistry with an explicit permission_callback. Two static contracts (routes-static.php, routes-collision.php) fail CI otherwise. /erase-lead now requires a dedicated secret plus a brute-force limiter (SE-016).
  • CSRF: all state-changing AJAX handlers use check_ajax_referer; admin actions use check_admin_referer and current_user_can('manage_options').
  • SQL: every query with external input uses $wpdb->prepare(). The raw queries found only interpolate internal table names.
  • Uploads: is_uploaded_file, size cap (10 MB), count cap (15), wp_check_filetype_and_ext against a MIME allow-list, wp_getimagesize dimension bounds, then media_handle_upload.
  • Command execution: single proc_open gateway (class-exec-whitelist.php) with absolute-path allow-list, optional SHA-256 pinning (PARTIKULIER_EXEC_REQUIRE_PIN), escapeshellarg on every argument, flag validation, timeout with SIGKILL.
  • Secrets: hash_equals everywhere, HMAC with timestamp window and key rotation, secret + mode off promoted to enforce, unknown Key-Id rejected (E-4905), secret strength check (≥ 32 bytes).
  • Personal data: phones hashed with HMAC for lookups and AES-256-GCM encrypted at rest; decryption restricted to manage_options; retention purge crons.
  • Exposure reduction: /wp/v2/users hidden from non-privileged users, ?author= enumeration blocked, XML-RPC disabled (including unauthenticated methods), X-Powered-By removed, HSTS on HTTPS, nosniff, X-Frame-Options.
  • Supply chain: packaging excludes tests, .git, .github, shell scripts and node_modules (checked in CI). Checksums are published.
